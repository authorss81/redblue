# The FRAGMENT bucket — documentation code blocks this suite does not execute.
#
# Read by `tests/doc_blocks_test.rs`. Every ```redblue block in SPEC.md,
# README.md, PHILOSOPHY.md, HANDOUT.md and docs/GRAMMAR.md must appear in
# exactly one of `this file` and `tests/doc_blocks_known_fail.txt`. A block in
# neither fails the suite, so neither list can quietly shrink.
#
# WHAT FRAGMENT MEANS
# The block is not executed, and the reason is written beside it. Two kinds of
# reason appear here, and they are not the same thing:
#
#   excerpt - the block is not a program. It has an elided `end`, a placeholder
#             body (`// statements`, `// ...`, `// Implementation`), or names
#             that only the surrounding prose introduces. Nothing about running
#             it is promised, so there is nothing for the interpreter to answer.
#
#   network - the block is a program, and it performs a live HTTP request. This
#             suite runs no network (AGENTS.md § 3.1.4), so the block is
#             classified rather than executed and its outcome is unverified.
#             Two entries below say so; a reader must not take them for
#             "this runs".
#
# A block that IS a whole program and still fails belongs in the KNOWN-FAIL
# file with the first line of stderr it prints today, not here. Calling a
# broken example a fragment is how a documentation promise rots unnoticed.
#
# FORMAT
#   <doc>:<line><TAB><reason>
# `line` is the line of the opening ```redblue fence, counted from 1. That
# makes the entry brittle on purpose: editing a document above a block moves it,
# and a moved block fails this suite rather than quietly losing its bucket.
#
