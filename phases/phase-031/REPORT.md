### Why `import files` / `import json` is no longer `Cannot find module`

A builtin namespace (`console`, `csv`, `files`, `json`, `network`, `time` —
`src/stdlib.rs:7`) has no file behind it, and the old arm refused anything
without one. The phase's own definition of done requires
`import json as J` to run, so a namespace is now importable under any alias.
**This is a previously-rejected program that is now accepted**, and it is the
one behaviour change here that could be called a regression; it is listed in
the gates table below and the error for a name that is *neither* a file nor a
namespace is unchanged and pinned by
`edge_unknown_import_name_is_an_error_that_names_it`.

### Rows from the phase's matrix that are N/A, and why

- **numeric_boundary** — nothing numeric was added. A module declaration binds
  names and copies values; no arithmetic, no division, no conversion. The one
  numeric-ish assertion, `M.circle_area(2)` → `12.56636`, is a decimal the
  module file itself declares, so the boundary being crossed is `f64`
  formatting, which `tests/numeric_edge_test.rs` already owns.
- **unicode** — module, alias, export and member names are identifiers, which
  `src/lexer.rs` restricts to `[A-Za-z_][A-Za-z0-9_]*`. A non-ASCII module
  name is a lexer-level decision that applies to every identifier in the
  language, not to modules; testing it here would test the lexer.
  `edge_module_declaration_without_a_name_is_refused` covers the adjacent case
  (a token that is not an identifier where one is required).
- **non-UTF8 / BOM / CRLF inside a module body** — the module body is ordinary
  source read by the same lexer as everything else;
  `tests/lexer_robustness_test.rs` and
  `tests/parser_hardening_test.rs` already own those bytes. Re-testing them
  through a module body would add no branch.

## Invariants touched

- None of the listed language invariants. `.rb` is unchanged, `end` still
  closes every block, `set x to …` is still assignment, `say` still prints,
  the `Value` and `Error` enums are untouched.
- One behaviour outside the module system changed, and it is a widening, not a
  narrowing: `import <builtin namespace>` was `Cannot find module '<name>'` and
  is now accepted. `AGENTS.md`'s own module-system section documents
  `import files, network as net` as working, and the phase's definition of
  done requires it, so the old refusal was the defect.
- No existing test was weakened, deleted, skipped, `#[ignore]`d or given an
  `allow(clippy::…)`. No timeout or threshold was moved. The diff adds no
  `#[ignore]`, no `.skip` and no clippy suppression.

## Known gaps / follow-ups

All four are in `FINDINGS.md` with file:line evidence:

1. **The bytecode VM has no module system.** `module … end` compiles as its
   body run inline and an import alias is not recorded at all, so
   `import json as J` then `J.stringify(2)` is
   `Unknown function 'J_stringify'` under `rb compile` / `rb vm` and `2` under
   `rb run`. This is why no Redblue `test` block was added to `tests/` — every
   `.rb` file there is corpus input to
   `a_corpus_of_programs_runs_identically_on_both_vms`, and the two VMs must
   agree. Adding `tests/test_modules.rb` to `NOT_COMPARABLE` would have made
   the gate green while hiding the divergence, which AGENTS.md rule 2 forbids.
2. `rb format` still writes `import X to Y` where the alias goes.
3. A module name is callable but not indexable: `J.PI` is
   `Cannot access property on non-object`.
4. `parser::module_body` ignores sibling top-level statements when a module
   file also holds them.
