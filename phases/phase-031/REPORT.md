# Phase 031 — Implement `module ... end`, `export`, and the `import X as Y` alias

Two runs. The first run added the feature to the parser, the tree-walking VM
and the module files. The second closed the gap that left behind: the bytecode VM
could not run a single one of the programs the first run introduced. A review of
the second run then found four defects in it, all now fixed; what they were and
how each was caught is below.

## Rows from the phase's matrix that are N/A, and why

- **numeric_boundary** — nothing numeric was added. A module declaration binds
  names and copies values; no arithmetic, no division, no conversion. The one
  numeric-ish assertion, `Geometry.area(2)` → `12.56636`, is a decimal the
  module itself computes, so the boundary being crossed is `f64` formatting,
  which `tests/numeric_edge_test.rs` already owns.
- **unicode** — module, alias, export and member names are identifiers, which
  `src/lexer.rs` restricts to `[A-Za-z_][A-Za-z0-9_]*`. A non-ASCII module name
  is a lexer-level decision that applies to every identifier in the language,
  not to modules; testing it here would test the lexer.
- **non-UTF8 / BOM / CRLF inside a module body** — the module body is ordinary
  source read by the same lexer as everything else;
  `tests/lexer_robustness_test.rs` and `tests/parser_hardening_test.rs` already
  own those bytes. Re-testing them through a module body would add no branch.
- **`.rbc` round trip** — `edge_a_decoded_chunk_runs_identically_to_the_compiled_one`
  already pins that a decoded chunk runs as the compiled one does, so the new
  `MODULE`/`EXPORT` instructions and `IMPORT`'s second operand are covered there
  for the encoding side.

## Invariants touched

- None of the listed language invariants. `.rb` is unchanged, `end` still closes
  every block, `set x to …` is still assignment, `say` still prints, the
  `Value` and `Error` enums are untouched.
- `.rbc` changed shape, deliberately and with a version bump: `FORMAT_VERSION` 3
  → 4, two new opcodes at bytes 47 and 48, and one new block kind at byte 7. No
  byte value already written into a file moved, and a version-3 file is refused
  rather than half-read — which is `docs/BYTECODE.md`'s rule 2, and the whole
  point of finding 1.
- One behaviour outside the module system changed in the first run, and it is a
  widening, not a narrowing: `import <builtin namespace>` was
  `Cannot find module '<name>'` and is now accepted. AGENTS.md's own
  module-system section documents `import files, network as net` as working, and
  the phase's definition of done requires it, so the old refusal was the defect.
  The error for a name that is *neither* a file nor a namespace is unchanged and
  pinned by `edge_unknown_import_name_is_an_error_that_names_it`.
- One existing test was re-pointed rather than deleted or weakened:
  `edge_the_constant_instruction_has_a_byte_of_its_own` in
  `tests/bytecode_test.rs` asserted `Opcode::ALL.len() == DeclareConst + 1`,
  which cannot hold once the table grows. Its assertion about `DECLARE_CONST` is
  unchanged — the byte is still 46 and still decodes back — and the new
  `edge_the_module_instructions_take_bytes_no_earlier_version_used` asserts the
  stronger property: every opcode in the table sits at the index its byte names.
- No existing test was weakened, deleted, skipped, `#[ignore]`d or given an
  `allow(clippy::…)`. No timeout or threshold was moved. The diff adds no
  `#[ignore]`, no `.skip` and no clippy suppression.

## Known gaps / follow-ups

All seven are in `FINDINGS.md` with file:line evidence:

1. `rb format` still writes `import X to Y` where the alias goes, because two
   existing formatter tests pin the `to` round trip.
2. A module name is callable but not indexable: `J.PI` is
   `Cannot access property on non-object`.
3. `parser::module_body` ignores sibling top-level statements when a module file
   also holds them.
4. The analyser does not see into a module file, so an imported name is usable
   only as a plain read at run time. Consistent on both VMs, so not a
   divergence.
5. `rbops/baseline.json`'s `unparseable` entry for `modules/MathUtils.rb` is
   stale and cannot be edited from this checkout.
6. A member call is resolved against the receiver's *name* — `CALL_METHOD`
   carries `receiver.method` — so a receiver that is an expression rather than a
   name has no spelling at all. Neither VM has one, so nothing disagrees.
